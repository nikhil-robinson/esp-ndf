# TLS 1.3 and HTTPS (own implementation) Implementation Plan

> Sub-plan of Task 13 in `2026-10-27-wireless.md`. Executed inline (superpowers:executing-plans).

**Goal:** TLS 1.3 client and server on esp-ndf with our own code (`components/tls`), HTTPS client and server on top of `components/net/http.c`, interoperating with OpenSSL on the host and with the IDF peer's `esp-tls` / `esp_https_server`.

**Architecture:** one sans-IO engine (`tls.c`): the caller feeds received bytes and sends what the engine has queued, so the same code runs over an lwIP raw TCP pcb on the board and over a socket in the host test. Single cipher suite TLS_AES_128_GCM_SHA256, key exchange X25519, signatures ecdsa_secp256r1_sha256, no PSK / resumption / 0-RTT / client certificates / HelloRetryRequest (a server that wants another group gets a clean `TLS_ERR_UNSUPPORTED`). Records are limited to 4096 bytes of plaintext with the `max_fragment_length` extension (RFC 6066), so one connection needs about 10 KB.

**Tech stack:** `aes_gcm`, `x25519`, `p256_*`, `sha` (SHA-256), `rng`; HMAC-SHA256 / HKDF written here (RFC 5869, RFC 8446 7.1).

**Spec:** RFC 8446 (TLS 1.3), RFC 8448 (example traces, used as test vectors), RFC 6066 (max_fragment_length), RFC 5280 (X.509, minimal subset).

## Global Constraints

- No windowed-ABI code, no IDF code on esp-ndf; reading IDF / mbedtls source for behaviour is allowed.
- Secrets are wiped with `explicit_bzero`-style volatile writes; the Finished and certificate-signature checks are constant time where they compare secrets.
- Every length from the wire is checked against the buffer before use (the engine is fuzzed).
- Certificates: DER, ECDSA P-256 public key, `ecdsa-with-SHA256`; the client verifies the server certificate against a pinned CA public key (leaf signed by the CA) or a pinned leaf (exact public-key match), and the host name against the SAN dNSName (or CN when there is no SAN). No RTC: validity dates are not checked (stated in the docs).

## Files

- Create `components/tls/{tls.c,tls_crypto.c,x509.c,include/tls.h,include/x509.h}`; `components/net/https.c` (HTTPS server/client glue on lwIP).
- Create `tools/fuzz/fuzz_tls.c`, `tools/tls_host_test.sh` + `tools/tls_host.c` (host driver against `openssl s_server` / `s_client`), `tools/wl/tls_certs.py` (CA + server certificate for the tests), `components/tls/test_apps/tls_unit` (RFC 8448 vectors on the board), `components/net/test_apps/https_unit` + `tools/wl/test_https.py`.
- Modify the IDF peer (`bench/idf_wl_peer`): `https_get`, `https_serve` commands, sdkconfig for TLS 1.3 and `esp_https_server`.

## Task A: crypto helpers and key schedule

- [ ] HMAC-SHA256, HKDF-Extract, HKDF-Expand-Label, Derive-Secret (`tls_crypto.c`), tests = RFC 8448 section 3 ("Simple 1-RTT Handshake") secrets: early secret, handshake secret, client/server handshake traffic secrets, keys and IVs, Finished keys, application secrets.
- [ ] Record protection: nonce = IV xor 64-bit sequence number, AAD = 5-byte header, inner content type, padding ignored; test with the RFC 8448 encrypted records.

## Task B: X.509 subset

- [ ] `x509_parse(der, n, &cert)`: tbsCertificate bounds, signature algorithm = ecdsa-with-SHA256, subject public key = id-ecPublicKey / prime256v1 uncompressed point, SAN dNSName list / CN, basicConstraints cA flag.
- [ ] `x509_verify(cert, ca_pub)` (ECDSA over SHA-256 of tbsCertificate), `x509_host_ok(cert, host)` with a single leading wildcard label.
- [ ] Tests: certificates made by `tools/wl/tls_certs.py` (valid; wrong CA; truncated at every byte offset; wrong host).

## Task C: handshake engine

- [ ] Client: ClientHello (supported_versions, supported_groups x25519, signature_algorithms, key_share, server_name, max_fragment_length), ServerHello, EncryptedExtensions, Certificate, CertificateVerify, Finished, client Finished; legacy session id echo; middlebox compatibility ChangeCipherSpec ignored.
- [ ] Server: same states in the other direction; the certificate and the P-256 key are given at init.
- [ ] Application data both ways, close_notify, alerts mapped to errors; KeyUpdate answered (request update_not_requested).
- [ ] Tests: RFC 8448 trace replay (fixed random / key shares injected through a test hook), then OpenSSL on the host both ways (`tools/tls_host_test.sh`): handshake, 1 MB each way, wrong CA fails, wrong host fails, truncated / flipped bytes in every record fail closed.
- [ ] Fuzz: `tools/fuzz/fuzz_tls.c` feeds random and mutated flights to client and server engines under ASan/UBSan (security-test).

## Task D: HTTPS on lwIP and the peer

- [ ] `https.c`: the HTTP server and client use a transport vtable (plain TCP or TLS over the pcb); `https_server_start(port, cert, key)`, `https_get(url, ...)` with the pinned CA.
- [ ] Peer: `https_serve` (esp_https_server, same CA-signed ECDSA certificate) and `https_get` (esp_http_client with `cert_pem` = our CA); `test_https.py`: ndf client to the IDF server, IDF client to the ndf server, wrong-CA failure on both.
- [ ] PERFORMANCE.md: handshake time, ECDSA verify / sign, X25519, AES-GCM record throughput vs mbedtls on the same chip (IDF peer on the DEVKIT board class).

## Review Focus

- A server that sends a HelloRetryRequest, a TLS 1.2 ServerHello, or an unsupported cipher suite must end in a clear error, never in a stuck state.
- A Certificate message longer than the record buffer or a chain with more certificates than we parse must fail closed.
- Sequence-number exhaustion (2^64) is unreachable; a record with a bad tag must wipe the output and close the connection.
- Two connections at once are not supported in v1 (one `tls_t`), documented.
